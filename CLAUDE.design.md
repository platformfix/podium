# CLAUDE.md design notes

## Purpose

This CLAUDE.md optimizes for one thing: a future agent (most likely another Claude Code session of Steve's, possibly a contributor's) picking up work on a *public, reputation-bearing* repo without re-discovering the same bugs and dead ends that were already worked through once, live, against real infrastructure. Podium has no skills directory of its own — it's a plain open-source project — so the offload target for situational detail is the existing `docs/*.md` split (architecture, configuration, supply-chain) plus `CONTRIBUTING.md`, not a skills system. CLAUDE.md stays the index; those files stay canonical for their topics.

Because this repo is public, the file also had to be written assuming its reader might not be Steve's own Claude Code session — so it avoids referencing Steve's personal tooling (AgenC, `bd`/beads, the `/writing-antipatterns` slash-skill by name) as anything load-bearing. Where a personal skill would normally be the natural pointer, the guidance is written as a self-contained principle that degrades gracefully for a reader who doesn't have that skill.

## Design decisions

- **No bead/AgenC/personal-tool references.** Steve's global CLAUDE.md governs those universally for his own sessions; podium is a public repo, and a reference to `bd` or an AgenC mission UUID would be dead on arrival for any other reader. Left out entirely rather than offloaded, since there's no non-personal equivalent to point to.
- **The five "constraints that matter" are the load-bearing set, chosen because each one already caused a real, verified failure in this repo's history** (fabricated commit SHAs breaking CI twice; the attach/exec syntax bug the user hit live; the pullPolicy staleness trap; the CODEOWNERS deadlock; the rejected-but-tempting "start fresh" Scorecard idea) **or guards a genuinely irreversible-ish outcome** (`pull_request_target` + secrets exposure on a public repo taking outside contributions). Nothing was included on the theory that it "seemed like good practice" — everything traces to something that actually happened this session, which is also why each bullet states the why and the incident, not just the rule.
- **The review-requirement note is phrased as "by design, not oversight."** Without that framing, a future agent (or Steve, a year from now) skimming the ruleset and seeing `required_approving_review_count: 0` could reasonably "fix" it back to 1, recreating the exact deadlock this session spent real effort resolving. The note carries the actual reasoning (solo-author repo, GitHub's own approve-your-own-PR block) so the decision can be revisited correctly rather than reverted blindly.
- **Considered and rejected: duplicating the Helm values table or the architecture diagram into CLAUDE.md.** Both already have a canonical home (`docs/configuration.md`, `docs/architecture.md` respectively) and are situational — not needed in most sessions, and any duplication would drift the moment one copy got edited and the other didn't (the Echo Chamber antipattern). Routing entries only.
- **Why the Scorecard "start fresh" reset was rejected (the source the CLAUDE.md bullet points to).** Proposed as: squash all git history to one commit, delete and re-push every image tag and chart version, on the theory that a clean slate would raise the OpenSSF Scorecard score faster than fixing findings individually. Checked against what each low-scoring check (Dangerous-Workflow, Token-Permissions, Pinned-Dependencies, SAST, Signed-Releases, Branch-Protection, Code-Review, Maintained, Contributors) actually evaluates: every one of them reads current file/workflow/config state or current release metadata, not commit count or history depth. The one check that does look at history — Maintained, which scores commit *frequency over time* — would have been made worse by a squash, not better, since it erases the record of ongoing activity the check is trying to measure. Net: zero score benefit, real cost (destroys real signed-commit history, invalidates already-issued attestation references, pure wasted effort). Rejected on that evidence; the actual score improvement (4.1 → 6.5/10 across PRs #8–#10) came from working each finding against its real check semantics instead.
- **Considered and rejected: a numbered "workflow" for how to add a new CI check or bump a chart version.** Both are one-way procedures the author could easily have prescribed, but neither protects against a real, evidenced failure — they'd just be encoding one path an agent already capable of reading the existing workflows would find anyway. Left as discoverable from the repo rather than scripted.
